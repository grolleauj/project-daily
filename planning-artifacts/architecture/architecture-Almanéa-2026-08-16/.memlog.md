# Memlog — Almanéa Architecture

## Decisions

### AD-1 — Modular Monolith Paradigm
- **Type**: decision
- **Text**: Adopt Modular Monolith as the architectural paradigm for Almanéa. All engines (Context, Recommendation, Knowledge, Generation) are modules within a single deployable unit.
- **Binds**: Context Engine, Recommendation Engine, Knowledge Engine, Generation Engine, User Management, Gamification, Notifications, Web UI
- **Prevents**: Divergence in deployment units or inter-module communication protocols.
- **Rule**: All modules must expose clear interfaces (Python abstract base classes or protocols) and communicate via well-defined contracts (e.g., `UnifiedContext` for Context Engine → Recommendation Engine).
- **Status**: [ADOPTED] (from PRD: "Modular Monolith")

### AD-2 — Provider-Agnostic Adapters
- **Type**: decision
- **Text**: Each external data provider (Atmo France, RTE, Hub'Eau, OSM) must have a dedicated adapter implementing a common `ProviderAdapter` interface.
- **Binds**: Context Engine, FR-1, FR-2, FR-3, FR-5
- **Prevents**: Vendor lock-in and inconsistent data fetching/normalization across providers.
- **Rule**: Adapters must implement: `fetch()`, `normalize()`, `validate()`. All provider-specific logic (API keys, rate limits, data formats) is encapsulated in the adapter.
- **Status**: [ADOPTED] (from PRD: "Provider-agnostique")

### AD-3 — LLM-Agnostic Generation
- **Type**: decision
- **Text**: Generation Engine uses an `LLMProvider` interface to abstract all LLM interactions.
- **Binds**: Generation Engine, FR-14, FR-15, FR-16
- **Prevents**: Dependency on a specific LLM vendor (e.g., OpenAI, Anthropic).
- **Rule**: `LLMProvider` must expose: `generate(prompt: str, context: dict) -> str`. Fallback to deterministic explanations if LLM is unavailable (FR-16).
- **Status**: [ADOPTED] (from PRD: "LLM-agnostique")

### AD-4 — Unified Context Contract
- **Type**: decision
- **Text**: Context Engine outputs a standardized `UnifiedContext` object consumed by Recommendation Engine.
- **Binds**: Context Engine, Recommendation Engine, FR-4
- **Prevents**: Inconsistent data formats between engines.
- **Rule**: `UnifiedContext` must include: `observations` (list of `Observation`), `user_profile` (optional), `timestamp`. Each `Observation` contains: `provider`, `observedAt`, `retrievedAt`, `expiresAt`, `quality`, `value`.
- **Status**: [ADOPTED] (from PRD: "Unified Context")

### AD-5 — Deterministic Recommendations
- **Type**: decision
- **Text**: Recommendation Engine must generate recommendations deterministically (without LLM) for reproducibility.
- **Binds**: Recommendation Engine, FR-6, FR-7, FR-8, FR-10
- **Prevents**: Non-reproducible or flaky recommendation generation.
- **Rule**: Scoring formula is fixed: `Score = 25% ContextFit + 20% TimeFit + 15% UserPreference + 15% Accessibility + 10% EnvironmentalOpportunity + 10% WellbeingOpportunity + 5% Novelty`. All inputs to the formula must be deterministic.
- **Status**: [ADOPTED] (from PRD: FR-10)

### AD-6 — Rule Engine Priority
- **Type**: decision
- **Text**: Rule Engine applies rules with a strict priority order to resolve conflicts.
- **Binds**: Recommendation Engine, FR-9
- **Prevents**: Conflicting recommendations (e.g., suggesting outdoor activity during poor air quality).
- **Rule**: Priority order: 1) Safety (e.g., air quality), 2) Legal restrictions (e.g., water bans), 3) Technical constraints (e.g., missing data), 4) User preferences.
- **Status**: [ADOPTED] (from PRD: FR-9)

### AD-7 — Caching Strategy
- **Type**: decision
- **Text**: Context Engine caches normalized data in Redis to avoid repeated API calls.
- **Binds**: Context Engine, FR-3
- **Prevents**: Rate limit issues and unnecessary external API calls.
- **Rule**: Cache TTL: 5 minutes for real-time data (e.g., air quality), 1 hour for static data (e.g., lunar phases). Fallback to last valid cached value if provider fails.
- **Status**: [ADOPTED] (from PRD: "Cache et bases de données")

### AD-8 — Alert Delivery SLA
- **Type**: decision
- **Text**: Critical alerts (e.g., poor air quality) must be delivered in <5 minutes.
- **Binds**: Notifications, FR-32
- **Prevents**: Late delivery of time-sensitive alerts.
- **Rule**: Use async message queue (RabbitMQ) + dedicated workers (Celery) for alert processing. Cache alerts in Redis to avoid duplicates. Prioritize critical alerts over non-critical ones.
- **Status**: [ADOPTED] (from PRD: FR-32)

### AD-9 — Gamification Determinism
- **Type**: decision
- **Text**: Gamification (points, badges) must be fully deterministic and LLM-free.
- **Binds**: Gamification, FR-21, FR-22, FR-23, FR-24, FR-25, FR-26, FR-27, FR-28, FR-29, FR-30
- **Prevents**: Inconsistent or unfair point/badge allocation.
- **Rule**: Points are calculated server-side using fixed rules (e.g., +120 points for bike ride). Badges are awarded based on predefined thresholds (e.g., 5 repairs = "Réparateur" badge).
- **Status**: [ADOPTED] (from PRD: "Le LLM n'est pas utilisé pour les calculs de points")

### AD-10 — Web UI Mobile-First
- **Type**: decision
- **Text**: Web UI (Next.js) follows a mobile-first responsive design.
- **Binds**: Web UI, FR-34, FR-35, FR-36
- **Prevents**: Poor user experience on mobile devices.
- **Rule**: Use TailwindCSS for styling. Navigation: 5 bottom tabs + floating central button for actions. Prioritize touch-friendly interactions.
- **Status**: [ADOPTED] (from PRD: "Priorité mobile-first")

## Constraints

### C-1 — No Vendor Lock-In
- **Type**: constraint
- **Text**: Avoid dependency on specific vendors for APIs (providers) or LLMs.
- **Source**: PRD ("Provider-agnostique", "LLM-agnostique")

### C-2 — Deterministic Core
- **Type**: constraint
- **Text**: Core functionality (recommendations, scoring, gamification) must be deterministic and testable without external dependencies (e.g., LLMs).
- **Source**: PRD (FR-10, FR-16)

### C-3 — SLA for Alerts
- **Type**: constraint
- **Text**: Critical alerts must be delivered in <5 minutes.
- **Source**: PRD (FR-32)

### C-4 — Positive-First UX
- **Type**: constraint
- **Text**: All recommendations and notifications must avoid guilt-tripping users. Focus on opportunities, not restrictions.
- **Source**: PRD ("Approche positive first")

## Assumptions

### A-1 — Deployment
- **Type**: assumption
- **Text**: Initial deployment targets a single server (Modular Monolith). Horizontal scaling is deferred to GA phase.
- **Revisit**: If traffic exceeds 10K daily active users.

### A-2 — Data Volume
- **Type**: assumption
- **Text**: Daily data volume from providers is <100K observations. PostgreSQL + Redis can handle this without sharding.
- **Revisit**: If volume exceeds 1M observations/day.

### A-3 — LLM Usage
- **Type**: assumption
- **Text**: LLM is only used for generating explanations (Generation Engine). Core logic (recommendations, scoring) is LLM-free.
- **Revisit**: If user feedback indicates explanations are insufficient without LLM.

### A-4 — Provider APIs
- **Type**: assumption
- **Text**: All provider APIs (Atmo France, RTE, Hub'Eau, OSM) remain free and publicly accessible for PoC phase.
- **Revisit**: If any provider introduces rate limits or costs that exceed PoC budget.
